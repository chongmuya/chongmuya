# 협업 규칙

총무야의 커밋·브랜치·PR 작성 기준입니다. 설치와 실행은 [README](../README.md)를 참고하세요. 규칙 설명은 이 문서에, PR 입력 양식은 [GitHub 템플릿](../.github/pull_request_template.md)에 둡니다.

## 개발 도구

- `.nvmrc`와 `packageManager`의 버전으로 `pnpm install --frozen-lockfile`을 실행하면 Git hook도 준비됩니다. CI와 프로덕션 설치에서는 hook 준비를 건너뜁니다.
- `pnpm format`으로 포맷하고 `pnpm format:check`로 확인합니다. 생성물과 lockfile은 제외합니다.
- pre-commit은 스테이징된 지원 파일만 포맷합니다. lint-staged 기본 백업과 부분 스테이징 보호를 사용합니다. 전체 lint·타입 검사·테스트·빌드는 CI에서 실행합니다.

## 커밋 메시지

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/) 형식을 사용합니다. 타입과 scope는 영어 소문자, 설명과 본문은 한국어로 작성합니다. 코드 식별자와 도구 이름은 원문을 유지합니다.

```text
type(scope): 한국어 변경 요약

필요할 때 변경 이유와 중요한 제약을 설명합니다.
```

- 콜론 앞에는 공백을 넣지 않고 뒤에는 공백 하나를 둡니다. `chore(repo): 개발 환경 구성`처럼 작성합니다.
- scope는 변경 위치가 명확하면 사용합니다. 여러 영역에 걸쳐 특정 범위를 고르기 어려우면 생략할 수 있습니다.
- 제목은 한 줄로 핵심 결과를 적고 마침표는 생략합니다. `수정`, `작업`, `완료`만 적지 말고 무엇이 바뀌었는지 설명합니다.
- 하나의 커밋에는 함께 설명하고 되돌릴 수 있는 변경을 묶습니다. 관련 없는 정리와 기능 변경은 나눕니다.
- 본문은 제목만으로 의도가 충분하지 않을 때 작성합니다. 모든 커밋에 긴 본문이나 이슈 번호를 강제하지 않습니다.

### 타입

| 타입       | 사용 시점                       | 예시                                      |
| ---------- | ------------------------------- | ----------------------------------------- |
| `feat`     | 사용 가능한 기능 추가           | `feat(web): 예약 목록 화면 추가`          |
| `fix`      | 잘못된 동작 수정                | `fix(api): 중복 참석 요청 처리 오류 수정` |
| `docs`     | 문서·협업 가이드·PR 템플릿 변경 | `docs(repo): 커밋과 PR 작성 규칙 추가`    |
| `refactor` | 기능 변화 없는 코드 구조 개선   | `refactor(api): 참석 상태 계산 로직 분리` |
| `perf`     | 성능 개선                       | `perf(web): 예약 목록 중복 요청 제거`     |
| `test`     | 테스트 추가·수정                | `test(api): 참석 취소 실패 사례 추가`     |
| `build`    | 빌드 도구·의존성 변경           | `build(deps): Next.js 패치 버전 업데이트` |
| `ci`       | CI 설정 변경                    | `ci(repo): 타입 검사 워크플로 추가`       |
| `style`    | 동작에 영향 없는 코드 서식 변경 | `style(web): 들여쓰기 형식 정리`          |
| `chore`    | 초기 구성 등 나머지 유지보수    | `chore(repo): 초기 모노레포 구성`         |

화면의 디자인·동작 변경은 `style`로 분류하지 않습니다. 사용자 기능 추가인지 오류 수정인지에 따라 `feat` 또는 `fix`를 사용합니다. 위 예시는 작성법을 설명하며 해당 기능이나 CI가 구현됐다는 뜻은 아닙니다.

scope는 현재 구조에 맞춰 `web`, `api`, `repo`, `deps`를 우선 사용합니다. 새 업무 영역이 생기면 의미가 명확한 scope를 추가할 수 있습니다.

호환성을 깨는 변경은 `!`와 본문의 `BREAKING CHANGE:`로 영향 및 대응 방법을 설명합니다. 예: `feat(api)!: 참석 상태 응답 형식 변경`. 자동 버전 발행 도구는 현재 도입하지 않았습니다.

## 브랜치와 작업 흐름

- `main`을 기준으로 짧게 사용하는 작업 브랜치를 만들고 PR로 병합합니다. 별도의 `develop` 브랜치는 두지 않습니다.
- 이름은 `타입/영문-kebab-case`로 작성합니다. 예: `feat/reservation-list`, `fix/attendance-duplicate`, `docs/contributing`.
- 진행 중이거나 방향에 대한 피드백이 필요하면 Draft PR을 엽니다. 검증과 자기 검토를 마쳤으면 Ready for review로 전환합니다.
- 한 PR은 하나의 목적을 중심으로 구성합니다. 무관한 변경은 분리하되, 동작하는 단위가 깨질 정도로 잘게 나누지는 않습니다.

첫 PR을 만들 때 원격 저장소가 비어 있어 비교 기준용 빈 초기 커밋으로 `main`을 만들었습니다. 이는 최초 초기화에만 해당하며 이후 변경은 PR로 반영합니다.

## PR 작성

제목도 커밋과 같은 형식을 사용하며 **PR 전체의 최종 결과**를 설명합니다. 작업 중 범위가 바뀌면 제목과 본문도 수정합니다. `WIP`를 제목에 붙이는 대신 GitHub의 Draft 상태를 사용합니다.

본문은 다음 세 항목을 기본으로 합니다.

| 항목      | 작성할 내용                                                                              |
| --------- | ---------------------------------------------------------------------------------------- |
| 변경 내용 | 해결하려는 문제·필요한 이유와 변경 후 동작. 설정·호환성 영향이 있으면 함께 설명          |
| 확인 방법 | 실제 실행한 명령 또는 재현 절차, 기대 결과와 실제 결과. 미실행·실패한 검증은 이유를 명시 |
| 관련 이슈 | 완료하는 이슈는 `Closes #번호`, 단순 참고는 `관련: #번호`, 없으면 `없음`                 |

`Closes`는 이 PR이 이슈를 실제로 해결하고 기본 브랜치에 병합될 때만 사용합니다. 형식을 채우려고 이슈를 새로 만들거나 임의의 번호를 넣지 않습니다.

화면 변경이 있으면 필요한 전후 스크린샷을, 실행 설정이 바뀌면 적용 방법을 **변경 내용**에 추가합니다. 해당하지 않는 항목을 위해 빈 섹션이나 긴 체크리스트를 만들지 않습니다.

### 작성 예시

제목: `fix(web): API 연결 실패 상태 표시 수정`

```markdown
## 변경 내용

- API가 중단되어도 성공 상태가 남는 문제를 수정했습니다.
- 요청 실패 시 실패 상태를 표시하고, API 재시작 후 다음 확인에서 복구합니다.

## 확인 방법

- 웹·API를 실행해 연결 성공 표시를 확인했습니다.
- API만 종료한 뒤 연결 실패, 다시 실행한 뒤 자동 복구를 확인했습니다.
- 실행한 린트·타입 검사 결과도 함께 기록합니다.

## 관련 이슈

없음
```

예시는 작성 형식이며 실제 PR에는 해당 변경에서 수행한 검증 결과를 적습니다.

## 검증과 리뷰·병합

- 리뷰 요청 전 diff를 직접 읽고 누락·불필요한 변경·환경변수 파일 포함 여부를 확인합니다.
- 앱 코드·의존성·빌드 설정 변경 시 루트에서 `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm test`를 실행합니다. DB 연결·스키마 변경은 격리된 로컬/테스트 DB의 `TEST_DATABASE_URL`을 지정해 `pnpm test:integration`도 실행합니다.
- 웹·API 연결 변경은 실제 실행과 성공·실패·복구를 확인합니다. 문서만 바꾸면 링크·내용·템플릿을 확인하고 불필요한 앱 빌드를 반복하지 않습니다.
- 다른 개발자가 참여하는 변경은 가능하면 작성자 외 1명의 리뷰 후 병합합니다. 혼자 작업할 때도 자기 검토와 검증 결과를 남깁니다.
- 기본 병합 방식은 **Squash and merge**입니다. 최종 커밋 제목을 PR 제목 규칙에 맞추고, 본문은 임시 커밋 목록 대신 필요한 맥락만 남깁니다. 병합 후 사용이 끝난 작업 브랜치는 정리합니다.
- 리뷰 중에는 추가 커밋으로 수정합니다. 공유 브랜치 이력을 임의로 덮어쓰지 않습니다.

커밋 형식은 문서와 템플릿으로 적용하며 commitlint는 사용하지 않습니다. GitHub Actions 검증 워크플로는 저장소에 정의되어 있지만, 필수 체크·필수 리뷰·브랜치 보호 규칙 설정 여부는 별도로 확인해야 합니다. Squash 병합 사용 원칙도 다른 병합 옵션을 비활성화했다는 뜻은 아닙니다.

PR 템플릿은 기본 브랜치에 병합된 뒤 새 PR 작성 화면에 자동으로 적용됩니다. 템플릿을 추가하는 첫 PR은 같은 형식으로 본문을 직접 작성합니다.
