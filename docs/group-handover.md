## 서버와 공개 계약

`handovers`는 기존 도메인의 공개 서비스를 조립한다. `groups`가 멤버십/초대/관리자 판정을, `events`가 실제 행사 소속과 행사 권한을 소유한다. 타 모듈 Entity를 참조하지 않는다. `favorites`는 개인 계정 또는 모임별 저장을 담당하고 매장 공개 projection만 사용한다.

| 경로                                                      | 계약                                                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `GET /groups/memberships`                                 | 본인의 모임 기본 정보와 역할만 반환                                               |
| `GET /groups/:id/accounts`                                | 현재 총무만 검증된 계정 멤버와 초대 상태 조회                                     |
| `POST /groups/:id/invitations`                            | 인증된 이메일 대상, 요청키·클라이언트 난수 토큰으로 24시간 초대 생성              |
| `POST /groups/invitations/:id/preview`, `/accept`         | 로그인 대상+목적 토큰 검증, 일반 멤버 가입; 재수락은 최소 영수증                  |
| `POST /groups/:groupId/invitations/:id/cancel`            | 현재 총무의 미수락 초대 취소                                                      |
| `PATCH /groups/:groupId/members/:memberId`                | 요청키/버전 검증, 기본 명단 수정·제외와 전후 감사 기록                            |
| `GET /handovers/groups/:id`, `POST /handovers/groups/:id` | 실제 이전 건수·이력 조회, 활성 계정 멤버로 이전 요청                              |
| `POST /handovers/groups/:groupId/:id/cancel`              | 아직 수락하지 않은 요청 취소                                                      |
| `POST /handovers/:id/preview`, `/accept`                  | 수신 계정·토큰·만료·그룹 버전·현재 관리자 검증 후 원자적 수락                     |
| `GET /favorites`, `POST /favorites`                       | 개인 또는 명시적 groupId 컨텍스트, 멱등 저장/해제; 비공개·삭제 매장은 placeholder |

모임·행사·기타 일정의 `creatorId`는 불변이다. 기존 `ownerId`는 현재 관리자 projection으로 유지한다. 수락 트랜잭션에서 모임 관리자, ADMIN/MEMBER, 모든 연결 행사의 현재 관리자와 버전, 모임 일정의 관리자와 버전을 바꾼다. 개인 행사·일정은 제외한다. 생성 요청키는 `(creatorId, creationKey)`를 기준으로 보존하며 과거 생성 재시도에도 현재 권한을 먼저 확인한다.

잠금 순서는 **실제 모임 → 행사(id 순) → 업무 자원**이다. 행사 소속은 서버의 저장된 groupId로 확인한다. 예약·정산·참석·명단·첨부 완료·기타 일정·리마인더가 같은 공개 잠금을 사용한다. 인수 수락과 구 총무 쓰기가 겹치면 먼저 확보한 모임 잠금의 트랜잭션이 끝난 후 다음 요청의 현재 권한을 다시 판단한다. 새 총무가 다시 넘긴 이후에도 이전 수락의 동일 실행자/키/digest 재시도에는 요청 ID·상태·완료 시각만 반환한다.

기본 명단 제외는 soft exclusion이고 이전 행사 participantId/이름/참석/부담자 snapshot을 변경하지 않는다. 명단 편집은 이전 값과 결과를 별도 이력으로 남긴다. 모임 즐겨찾기의 최초 저장자는 감사 필드로 유지하며 그룹의 현재 총무만 이용한다.

## 예약·정산·알림·파일

- 기존 예약 문의의 원래 연락처·snapshot, 예약금 실제 확인자, 결제/정산문 작성자, 파일 ID와 생성자를 그대로 둔다. 예약의 현재 담당자 계정·이름·전화번호만 바꾸고 인수인계 ID·이전/신규 담당자·시각·기록자를 남긴다. 사장님의 현재 담당자 표시와 향후 알림 수신자가 일치한다.
- 미발송 PENDING/HELD 및 명백한 SUBMISSION 실패만 새 담당자에게 재계획한다. 기존 행은 수신자 변경 사유로 보류하며 새 수신자 snapshot을 별도 기록한다. ACCEPTED/DELIVERED/UNKNOWN/PROCESSING은 재작성하거나 자동 재전송하지 않는다. 발송 직전 현재 담당자를 다시 비교한다. 커밋 이후에 기존 가짜/실 공급자 경계로 발송한다.
- 이전 총무의 개인 기본 정산 계좌는 복사하지 않는다. 새 총무의 신규 정산문은 현재 입력으로 계좌를 확인한다. 기존 정산문 원문/계좌는 그대로 두고 작성 총무가 달라진 생성본도 재확인이 필요한 문서로 표시한다.
- 이후 행사/정산/첨부 알림과 KST 리마인더는 변경된 현재 관리자에게 기록된다. PR4의 활성 화면 30초 unread 갱신과 열린 알림함 목록 정책은 유지한다. 과거 알림은 당시 기록이며 클릭한 자원에서는 현재 권한을 재검사한다.
- 비공개 첨부 다운로드는 기존 API의 현재 행사 권한 검사와 읽은 뒤 재검사를 유지한다. 업로드 완료 시도도 같은 트랜잭션에서 현재 권한을 다시 검사한다. 이미 공급자에 올라갔지만 권한이 바뀐 업로드는 임의 성공 처리하지 않으며 기존 UPLOADING 복구/삭제 계약으로 현재 관리자가 정리할 수 있다.
- 인수인계 전 이미 받은 화면·다운로드 바이트·SMS나 공급자 통신 중인 요청은 소급 회수하지 못한다. 기존 참가자/사장 링크는 원래 제한된 목적을 유지하며 관리자 링크로 승격하지 않는다.
- 웹은 계정별 Query key를 유지한다. 인수인계 완료 broadcast 또는 관리 API의 403/404에서 관리 화면을 닫고 사용자 Query/mutation 캐시를 비운다. 권한 세대가 바뀐 뒤 도착한 성공 응답도 거절한다. 다른 기기의 기존 총무는 다음 서버 요청에서 차단된다.

## 전진 migration과 운영 경계

`1795763000000-GroupHandover`는 기존 owner를 확인 가능한 creator로 backfill하고 기존 모임 owner의 ADMIN 멤버십을 만든다. 기본 명단과 개인 행사 groupId는 유지한다. 새 테이블은 memberships/invitations/handovers/roster edits/favorites이며 기존 자료를 복제하지 않는다. 불변 creator DB trigger는 생성 당시 값을 보존한다. 운영 DB에서 실행하지 않았다. 감사 자료를 버리는 down은 거절한다.

새 환경변수와 외부 공급자/인프라는 없다. 배포 담당자는 백업·스테이징 migration 검증 후 migration → 모든 API 인스턴스 교체 → 웹 순서로 적용한다. 이전 API 쓰기 인스턴스가 남아 있는 동안 새 인수인계 경로를 공개하지 않는다. 이전 단계 API에는 모임 잠금 보장이 없으므로 신구 API 혼용 중 인수인계를 허용하지 않는다. 수락 이후에는 소유자 변경을 되돌리는 DB 작업 대신 새 총무가 같은 명시적 인수인계 절차를 사용한다.

검증 결과와 실기기/실공급자 미실행 항목은 PR 본문에 분리해 기록한다. 이 작업은 Draft PR만 게시하며 운영 migration·스케줄 배포·실제 초대·문자·메일·송금은 수행하지 않는다.
