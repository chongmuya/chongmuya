# 회원 탈퇴

마이페이지의 **회원 탈퇴**에서 안내를 확인한 뒤 한 번 확인한다. 서버는 요청자의 현재 세션과 책임을 트랜잭션 안에서 다시 검사한다. 예약·소유권 차단으로 운영 검토를 접수한 동안에는 일반 기능을 이용할 수 있다. 차단 조건이 해소되면 사용자가 회원 탈퇴 화면에서 상태를 새로 확인하고 다시 요청한다.

## 서버의 차단 기준

| 저장된 상태                                                      | 처리                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reservation_requests.ACTIVE`, 열린 후보, 유효한 미래 일정       | 응답을 기다리거나 현재 제안을 수락할 수 있으면 진행 중 문의로 계산한다. 응답이 있으면 제안 일시와 제안의 유효기간을 사용한다. 문의 한 회차는 한 건이다.                                                                                                                                                                                                 |
| 문의 `CLOSED`·`SELECTED`, 종료·거절·만료된 후보, 지난 문의       | 진행 중 문의에서 제외한다. `SELECTED` 회차의 예약은 아래 저장 상태로 따로 판단한다.                                                                                                                                                                                                                                                                     |
| `selected_reservations.PREPARING`·`CHECK_REQUIRED`·`CONFIRMED`   | 취소되지 않은 예약은 종료 시각 전까지 진행 중이다. 시작 시각은 최신 합의, 최초 제안, 문의 순으로 확인한다. 합의된 이용 시간이 양의 분 단위면 시작에 더한 시각을 사용한다. 미확인·제한 없음·미기록 등 양의 이용 시간이 없으면 예약 시작일의 다음 날 00:00(한국시간, `Asia/Seoul`)을 사용한다. 수락 대기 중인 미래 일정 변경 제안도 진행 중으로 계산한다. |
| `CANCELLED`, `cancelled_at`이 있는 예약, 종료 시각에 도달한 예약 | 취소가 확정되면 해당 예약에 따른 차단을 즉시 해제한다. 종료 시각 정각부터도 해당 예약을 진행 중으로 계산하지 않는다. 환불·반환, 정산 또는 행사 마무리의 미완료로 차단하지 않는다.                                                                                                                                                                       |

종료 시각의 경과는 회원 탈퇴 가능 여부를 판단하는 데만 사용한다. 현재 행사 관리자, 예약의 현재 연락 담당자, 해당 대상 매장의 현재 소유자에게만 위 기준을 적용한다. 과거 생성자·선택자, 일반 모임 멤버, 다른 매장의 예약은 해당되지 않는다. 행사 관리 권한이나 매장 소유권이 있을 때만 해당 예약 확인 링크를 제공한다.

한 계정이 모임의 현재 유일한 관리자이거나 등록 매장을 소유하는 경우 별도로 운영 검토가 필요하다. 두 경우 모두 마이페이지에서 요청을 접수한다. 진행 중 예약·문의, 입금·반환, 발송 기록 및 모임·매장 권한은 탈퇴 동작으로 갱신하지 않는다.

문의 생성, 종료된 제안 재개, 선택, 예약 일정 변경 제안 및 새 합의 적용은 기존 모임 → 행사 → 업무 자원 순서를 사용하고 책임 계정 잠금을 획득한 뒤 기록한다. 탈퇴는 동일 계정 잠금을 획득한 뒤 업무 상태를 조회한다. 탈퇴 트랜잭션은 업무 자원 행을 잠그지 않는다. 문의나 책임이 먼저 저장되면 탈퇴 검사에 반영되며, 탈퇴가 먼저 확정되면 이후 쓰기 경로의 계정 재검증이 실패한다.

## 웹 접수와 운영 검토

같은 접수 키 및 중복 접수는 기존 건을 반환한다. 운영 검토는 접수 건에 처리자와 처리 시각을 기록한다. 검토 결과와 예약 종료는 탈퇴 확인을 대신하지 않는다. 회원이 직접 탈퇴하면 열린 접수 건을 종료한다.

DB 접근 권한이 있는 담당자가 접수 번호, 내부 계정 ID, 차단 범주와 시각을 확인한다. 로컬에서는 API 빌드 후 아래 명령을 실행하고, EC2에서는 [일회성 운영 명령](operations.md#ec2-일회성-명령)을 사용한다.

```bash
pnpm --filter @chongmuya/api account:withdrawals list
pnpm --filter @chongmuya/api account:withdrawals review <접수-UUID> --actor <운영자-식별자>
```

계정 처리 화면을 열 수 없으면 support@chongmuya.com으로 문의한다. 운영자는 연락 및 권한 확인을 기존 승인된 경로에서 진행한다. 모임 또는 매장을 맡길 수 없는 경우의 운영 기준과 접수 모니터링 담당자·응답 기한은 공개 전 확정한다.

## 카카오 연결 계정의 탈퇴 완료

예약·소유권 검사를 통과하고 회원이 탈퇴를 확인하면 계정 잠금 안에서 세션을 폐기하고 카카오 확인 작업을 저장한다. 이때 기존 카카오 연결 행 한 곳에 재시도에 필요한 앱 사용자 ID를 유지한다. 그 ID를 별도의 작업 행에 복사하지 않는다. 확인 중에는 총무야 사용, 로그인, 기존 카카오 연결의 재사용과 새 예약 책임 배정이 차단된다. 어드민 키가 처음부터 없으면 작업을 시작하지 않아 사용자가 기존 세션으로 다시 시도할 수 있다.

서버는 DB 잠금을 해제한 뒤 카카오 앱 사용자 ID를 조회하고, 일치하면 같은 서버 전용 어드민 키로 연결 해제를 요청한다. 연결 해제 응답의 ID가 일치하면 계정의 식별 정보와 로컬 카카오 연결을 지우고 완료로 표시한다. 카카오의 HTTP `400`과 오류 코드 `-101`은 앱에 연결된 사용자가 없다는 의미다. 해당 계정에 저장된 연결이 같고, 이 카카오 로그인 키와 어드민 키 조합에서 총무야에 저장된 앱 사용자 ID를 일치시킨 기록이 있을 때만 완료 근거로 사용한다. 이 확인 기록에는 앱 사용자 ID나 키 원문을 저장하지 않는다. 서비스에서 호출한 연결 해제의 최종 처리는 웹훅을 기다리지 않는다. [카카오 회원 탈퇴](https://developers.kakao.com/docs/en/kakaologin/common#account-deletion), [REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api#unlink), [오류 코드](https://developers.kakao.com/docs/ko/rest-api/error-code)

회원은 확인을 시작한 화면에서 **카카오 연결 해제 다시 확인**을 누를 수 있다. 카카오가 요청을 확실히 거절한 경우 원인을 해소한 뒤 다시 보낼 수 있다. 타임아웃이나 응답 유실로 처리 여부가 불명확하면 같은 변경 요청을 다시 보내지 않고 현재 연결을 조회한다. 조회 결과가 계속 연결 상태이면 운영자는 본인 확인을 거쳐 카카오 계정의 연결 서비스 관리에서 총무야 연결을 해제하도록 안내한 뒤 상태를 다시 확인할 수 있다. 해제 확인 전까지는 탈퇴 확인 중으로 표시한다. 완료 후 카카오로 돌아온 사람은 새 가입 절차를 별도로 확인해야 한다.

화면을 닫아 확인 키를 잃은 경우 DB 접근 권한이 있는 운영자가 아래 명령으로 대기 건을 확인하고 기존 확인 작업을 이어갈 수 있다. 목록에는 내부 계정 ID, 접수 시각, 연결 해제 전송 가능성, 현재 확인 작업의 잠금 만료 시각만 표시한다. 재시도는 웹과 같은 예약·소유권 검사와 카카오 확인을 수행한다.

```bash
pnpm --filter @chongmuya/api account:withdrawals kakao-list
pnpm --filter @chongmuya/api account:withdrawals kakao-retry <내부-계정-UUID>
```

공개 전과 카카오 어드민 키 또는 로그인 앱 구성을 교체한 뒤에는 지정 테스트 계정으로 실제 연결 해제 한 건을 검증한다. 서버에 현재 로그인 앱의 `KAKAO_ADMIN_KEY`를 주입하고, 해당 계정에 대해 카카오 연결 해제와 총무야 완료를 확인한다. 모의 공급자 테스트는 실제 앱의 키와 호출 권한을 검증하지 않는다.

## 데이터 처리와 공개 전 결정

| 범위             | 이 변경의 동작과 남은 결정                                                                                                                                                                                                                                                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 총무야 계정      | 완료 트랜잭션에서 이름·닉네임·이메일·연락처·비밀번호 해시·인증 출처와 시각·사장님 기본 예약금 계좌를 제거한다. 관계 무결성을 위해 기존 식별자와 예약 도메인의 대체 이메일 주소를 사용한다. 계정 연결·변경용 카카오 시도, 비밀번호 재설정 증명, 연락처 변경 증명을 삭제한다.                                                            |
| 인증 상태        | 기존 Access와 모든 Refresh 세션을 폐기하고 응답의 세션 쿠키를 제거한다. 더 이상 해당 계정으로 이메일 또는 연결된 카카오 로그인을 할 수 없다. 세션·Refresh 해시와 약관 동의 이력의 보존 목적, 기간과 정리 정책은 공개 전에 확정한다.                                                                                                    |
| 공동·업무 기록   | 예약·발송 기록, 공동 명단·정산·입금·증빙은 유지한다. 기록에 원래 연락처·입금 계좌·이름 등이 남을 수 있다. 자료 유형별 보존 목적과 필요성, 법적 기준, 제한된 접근권·분리 보관, 마스킹 또는 파기 시점과 작업 담당자를 확정한다. 개인 행사·개인 설정, 가입 인증 요청·익명 카카오 시도, 계정 연결이 없는 제공자 로그도 이 목록에 포함한다. |
| 완료 영수증      | 원래 브라우저가 만든 난수 키로 응답 유실 뒤 24시간 동안 완료 여부만 확인할 수 있다. 계정 정보나 접수 내역을 조회하는 권한을 부여하지 않는다. 해시 저장 기록과 접수·검토 감사 이력의 파기 주기는 공개 전에 승인한다.                                                                                                                    |
| 백업·외부 제공자 | DB·파일 복구 시 삭제 상태 재적용, 백업 수명·파기, Resend·Octomo 등 처리 위탁 기록의 범위와 정리를 결정한다. 카카오 연결 해제 절차와 공개 전 검증 항목은 위에 정리했다.                                                                                                                                                                 |

[개인정보 보호법 제21조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334901), [시행령 제16조](https://law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1032356231), [카카오 연결 해제 문서](https://developers.kakao.com/docs/ko/kakaologin/rest-api#unlink)를 기준으로 공개용 방침의 항목·기간·담당자와 구현을 일치시킨다.
