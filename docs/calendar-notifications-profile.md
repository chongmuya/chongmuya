# 캘린더·알림함·계정·매장 관리 (PR4)

PR3 검증 head `8989273f6195d37c9c4c9fb60ffe627e37713463`에서 시작한다. 비교 base는 `feat/settlement-records`, 구현 브랜치는 `feat/calendar-notifications-profile`이다. main 및 PR2/PR3를 병합하지 않는다. PR5 인수인계 UI·권한 이전 실행은 포함하지 않는다.

## 경로와 업무 계약

- `/calendar`: 개인 또는 선택 모임의 실제 행사와 기타 일정. 월 단위 조회는 한국 날짜 from(포함)/to(제외), 최대 62일이다. 행사 일정은 Events의 현재 값으로 조회하며 별도 복제하지 않는다. 시간 있는 일정은 절대 시각, 종일 일정은 PostgreSQL date로 보관한다. 월 경계와 정렬은 날짜/시각/ID로 안정화한다. 행사 추가·상세는 기존 `/events` 계약을 사용한다.
- 기타 일정: 이름 100자, 날짜, 시간/종일, 메모 100자. 생성은 계정+요청키 unique와 정규화 digest, 수정은 version 검증과 calendar_commands의 원본 요청 영수증, 삭제는 version 검증과 tombstone을 사용한다. 응답 유실은 원본 요청키/입력/버전을 고정해 재확인한다. 확정된 충돌은 최신 내용을 확인하고 명시적으로 재적용한다. 삭제 tombstone은 유지한다. 그룹 권한과 계정 권한은 서버에서 확인한다.
- `/calendar?restaurant=<id>`: 해당 소유 매장의 문의·선택·확정·취소·제안 만료. ReservationFactsService의 공개 조회로 제한하고 다른 후보의 조건을 노출하지 않는다. 별도 예약관리 링크 권한은 PR2와 동일하다. 외부 예약 장부/역경매/POS를 추가하지 않는다.
- `/notifications`: 계정별 커서 페이지(30건), 미읽음 수, 개별/전체 읽음. 계정 advisory lock 안에서 기록·설정·최신 sequence를 직렬화해 전체 읽음 snapshot 이후 도착한 항목은 남긴다. 알림 목적지는 내부 업무 경로와 UUID allowlist를 검증하며 최종 자원 권한은 대상 API가 다시 확인한다.
- 알림함의 수신 설정은 예약/정산/일정 3범주, 기본 켜짐이다. 설정과 기록은 같은 계정 잠금으로 직렬화한다. 설정으로 생성을 생략한 업무 fact도 남겨 같은 이벤트 재처리로 나중에 되살아나지 않는다. 기존 알림·업무 이력은 삭제하지 않는다. PR1/2 예약 운영 문자는 설정과 분리되어 있으며 UI에 명시한다. 새 정산·명단·파일·일정 이벤트를 SMS로 확대하지 않는다.
- 정산문 발행 시 미확인 대상이 있으면 정산 확인 알림, 계산 상태가 완료로 전환되면 완료 알림. 달력 날짜만으로 정산 알림을 반복 생성하지 않는다. 명단 추가와 첨부 READY 전환도 업무 트랜잭션에서 알림을 기록한다.
- 홈은 실제 행사와 참석·예약·정산 진행, 다음 행동, 알림 배지와 4개 탐색 항목을 연결한다. 사장 홈은 소유 매장의 이번 달 문의/예약과 캘린더/등록정보/메뉴/영업시간으로 연결한다.
- `/mypage?view=account`: 일반 프로필 명령을 첫 설정과 분리한다. 연락처 변경용 증명은 가입 테이블과 별도 `phone_changes`, `phone_change` purpose, 계정/현재 session/번호/5분 만료/횟수 제한에 묶는다. Octomo 외부 조회는 트랜잭션 밖, 재검증 후 Account → AuthSession → 증명 잠금으로 번호 변경과 소비를 원자 처리한다. 같은 소비 결과 확인은 번호를 재적용하지 않는다. 프로필과 번호 응답은 각각 바꾼 필드만 현재 계정에 반영한다. 변경 인증은 문자 앱/수동 SMS 안내를 제공하며 미사용 QR 공급자 호출에 의존하지 않는다. 다른 세션·번호·계정·가입 증명은 사용할 수 없다. 기존 문의·예약·매장 담당자 연락처 스냅샷은 수정하지 않는다.
- `/owner/hours?restaurant=<id>`: 7요일 대표시간 적용/영업/휴무, 익일 마감, 비정기 안내. 기존 policies JSONB를 확장하고 옛 등록 클라이언트가 저장해도 weeklyHours를 보존한다. 공개 매장 상세 설명도 같은 내용을 사용한다. 명시적인 OPEN/CLOSED가 우선이고 DEFAULT 요일만 기존 대표시간·구조화된 휴무를 적용한다. 공개 문구도 이 우선순위로 계산하고 원본 설문 텍스트를 덮어쓰지 않는다. 기존 대표시간과 선택 예약의 조건은 소급 수정하지 않는다.

## 브라우저 갱신과 서버 작업

웹은 활성 화면에서 미읽음 30초 갱신, 알림함에서는 최신 목록도 갱신한다. 인증된 앱 공통 위치에 계정별 미읽음 observer 하나를 두고 배지는 캐시만 구독한다. 과거 페이지는 탐색 시 조회하고 주기 조회를 추가하지 않는다. visibilitychange 복귀, focus, 네트워크 재연결 시 갱신한다. 숨긴 탭은 query 자체를 비활성화하여 초기 진입·재연결도 조회하지 않고 로그아웃/계정 전환은 기존 SessionClient의 사용자 query 취소·삭제와 화면 unmount를 사용한다. SSE/WebSocket은 없다. 이것은 서버 리마인더 실행과 무관하다.

리마인더 기본값은 `calendar/lib/calendar-time.ts`의 전날 09:00 Asia/Seoul이다. `REMINDERS_ENABLED=false`가 기본이며, true인 API 인스턴스는 매일 한국 시간 오전 9시에 다음 날 일정만 처리한다. 오전 9시 이후 시작하면 그날 배치의 미처리 항목을 한 번 보완하며, 9시 이전에는 정시 실행을 기다린다. 실패한 배치만 각 실패 후 1분·5분·15분 간격으로 최대 3회 추가 시도하고 한국 날짜가 바뀌면 종료한다. 정상 완료 후에는 다음 정시까지 조회하지 않는다. 다중 인스턴스는 원본 자원 행 잠금과 `reminder:<종류>:<ID>:<scheduleRevision>` fact unique로 중복을 막는다. 별도 영속 lease가 필요 없는 단일 DB 트랜잭션이며, commit 전 프로세스 종료는 rollback, commit 후 재시도는 fact로 복구한다. 새 일정/시간 변경이 이미 알림 시점 이후면 소급 생성하지 않는다. 행사/기타 일정의 시간 변경에만 scheduleRevision과 scheduleUpdatedAt을 갱신하며 이름·메모 수정은 미처리 리마인더 복구와 기존 fact를 보존한다. 삭제·현재 소유권·최신 일정 세대·설정을 commit 직전에 다시 확인한다. 개인 일정은 그룹 이전 대상이 아니다. PR5는 `CalendarService.transferGroup(groupId,from,to,manager)`를 같은 권한 이전 트랜잭션에서 호출할 수 있다.

## 전진 migration과 운영 점검

`1795761000000-CalendarInbox`는 기존 notification의 발생 시각을 fact에서 복원해 created_at으로 보존하고 sequence/read_at을 추가한다. 기존 항목은 읽음 여부를 추정하지 않고 미읽음으로 시작한다. 새 preferences/calendar_schedules/calendar_commands/phone_changes 테이블, Event의 schedule_updated_at을 추가한다. 과거 행사 알림을 몰아서 생성하지 않도록 기존 행의 schedule_updated_at은 migration 시각이다. 자동 synchronize/migrate는 없다. migration → 새 API 전체 전환 → 웹 → 리마인더 활성화 순서다. 새 자료가 생긴 뒤 down은 금지하며 보존 가능한 전진 복구를 한다.

관리 CLI는 공통 초기화에서 해당 프로세스의 `REMINDERS_ENABLED=false`를 Nest 초기화 전에 설정한다. API·Parameter Store 설정은 바꾸지 않는다. 수동 리마인더 CLI는 제거했으며 운영 이미지에는 관리 CLI 공통 초기화 파일을 포함한다. 이 변경에 별도 인프라·필수 환경변수·DB migration은 필요하지 않으며 새 API 이미지를 빌드·배포하면 된다.

운영 확인 항목: REMINDERS_ENABLED와 `REMINDER_RETRIES_EXHAUSTED` 오류 로그, API 서버 시각/DB 가용성, Octomo 설정·실기기 문자 앱과 번호 인증, 기존 SOLAPI 콜백, SIGNUP_TERMS_JSON의 실제 법률 문서/버전. 서버가 초안 약관을 반환하면 화면에도 초안임을 표시한다. 실제 SMS/메일, 운영 DB/인프라, 실기기 인증은 이 PR 테스트에서 실행하지 않는다.

## 검증 기록

Node 26.13.1 / pnpm 11.25.0에서 frozen install, format check, lint, typecheck, production build 및 단위 테스트(경계 8 / API 31 / 웹 121)를 실행했다. 새 격리 PostgreSQL 17에서 전진 migration과 전체 통합 65건이 통과했다. 마지막 DTO 보완은 시간대 없는 시각을 거절하며 캘린더 통합 6건을 재실행했다. 리마인더는 fake clock, 두 실행자, 커밋 직전 실패 후 재실행, 수신 설정 경합을 검증한다. 기존 예약 UNKNOWN/수령·반환·정산·파일 이력 회귀도 포함한다.

실제 로컬 Nest + PostgreSQL + Next production 서버를 Chromium에서 320/402/1280px로 검수했다. 기타 일정 생성·재조회·수정·삭제, 명단/정산 알림의 정확한 링크, 설정 저장·재조회, 프로필 수정과 합성 Octomo 번호 변경·재로그인, 익일 영업시간 저장·재조회가 통과했고 페이지 오류 및 가로 넘침이 없었다. 별도 합성 예약으로 매장답변→알림함→행사, 월력→행사→예약 확정, 사장 월력→해당 예약→은행 입금 확인을 연결 검수했다. 합성 공급자/합성 계정만 사용했으며 실제 은행 입금이나 SMS 송수신을 수행하지 않았다.

브라우저 검수는 production build를 사용했다. 실기기 문자 앱/QR, 실제 Octomo·SOLAPI·Kakao 운영 연결, 운영 스케줄 배포, 실제 약관/개인정보 문서 설정은 운영 담당자의 별도 확인 대상이다. Figma/Notion 원본 수정과 PR5 구현은 수행하지 않았다.

## 독립 검수 보완

`1795762000000-ReminderScheduleRevision` 전진 migration은 기존 행사·기타 일정의 version을 일정 세대로, 기존 일정 변경 시각을 일정 유효 시점으로 보존한다. 과거 메타데이터 수정 전에 유실된 시각을 추정하지 않으며 기존 알림 fact/문서/요청 영수증을 수정하지 않는다. 신규 작업부터 제목/메모와 시간 변경을 분리해 미발송 재시도 누락과 기발송 중복을 막는다.

삭제 409는 최신 상세와 초안을 함께 보여 주며 명시적으로 확인한 뒤에만 새 버전을 사용한다. 응답 유실은 원래 버전의 삭제를 재시도하고 확정된 400은 입력 수정 안내로 구분한다. 모임 일정 알림의 복귀 경로는 서버에서 권한을 확인한 상세의 groupId를 사용한다. 사장 월력은 기존 candidateState 계약을 호출하여 DECLINE을 MERCHANT_DECLINED(불가)로 표시한다.

추가 DOM/격리 DB 회귀는 숨김 초기 진입·재연결·복귀·로그아웃, 중복 배지의 단일 polling, 삭제 충돌·응답 유실, 프로필/번호 역순 응답, 빈 닉네임의 이름만 저장, QR 장애와 수동 인증 독립성, 제목·메모 수정 후 리마인더 복구 및 시간 변경/늦은 생성/삭제 제외, 불가 답변 월력과 명시 요일 우선순위를 확인한다. 실제 Chromium에서도 모임 deep link 복귀와 삭제 409→명시 확인→커밋 후 응답 유실→같은 삭제 재시도 및 행사 화면 공통 미읽음 조회를 검증했다.
